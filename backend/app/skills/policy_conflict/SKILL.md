# 多制度冲突检查

## 目标

识别多份制度中针对同一业务事项的规则冲突，重点关注审批主体、审批动作、适用范围、金额阈值、条件定义和优先级冲突。

## 输入

- `policy_ids`: 至少 2 份制度。
- 每份制度包含结构化条款：`id`, `clause_no`, `title`, `content`。

## 判断边界

- 执行前必须咨询流程管理知识库，获取制度解读、审批权限、合规管控和制度优先级判断框架。
- 只能根据输入的制度条款判断。
- 知识库用于专业判断、术语边界、治理建议和不确定性识别，不作为 finding 证据。
- 不得使用角色清单或其他中间层上下文作为结论证据。
- 不得把制度没有覆盖的事项直接判断为冲突；缺漏属于其他 skill。
- 若只存在表述差异但审批主体、动作、条件没有实质矛盾，不输出 finding。
- `questions` 只用于会改变判断结论的事实或语义不确定性，例如：两个相似角色/术语是否同义、制度版本/适用范围是否覆盖当前对象、引用文件是否属于本次证据范围。
- 不得把“是否补充制度条款、是否调整规则、是否修改流程节点、是否统一阈值”等整改动作写入 `questions`；这些应直接作为 finding 的风险描述或优化建议。

## 输出要求

输出 JSON 对象，字段必须符合 `schema.json`。

每个 finding 必须：

- 使用 `policy_conflict` 或 `authority_mismatch` 类型。
- 至少引用 2 条制度证据。
- 明确说明冲突事项、冲突字段和冲突后果。
- 按“风险描述、原文依据、判断假设、优化建议”组织内容：`description` 写风险描述，`evidence_ids` 对应原文依据，`assumption` 写判断假设，`suggestion` 写优化建议。
- 对已能基于所选制度条款判断的问题，必须输出 finding，不要改成让用户确认。

## 质量标准

- 优先少而准。
- 不输出没有证据的泛化风险。
- 证据必须能直接支撑冲突判断。
- 风险等级：审批主体或阈值冲突通常为 `high`；措辞/范围轻微不一致为 `medium`。
- 专业建议应体现知识库中的制度解读、合规管控或流程治理视角。
